# 4. Globální X04G → LX04

Převod globálního budíku na čínský systém. Je to nejtěžší část, protože globální kus má jiný paměťový čip a jiné rozložení oddílů.

> [!IMPORTANT]
> **K převodu potřebuješ `nvram` z opravdového čínského LX04.** Globální `nvram` neobsahuje identifikátor `mi.did` a čínský systém s ní skončí na hlášce „未发现mi.did" (mi.did nenalezen). Bez vlastního LX04 se převod dokončit nedá.

## Co budeš potřebovat

- [Zálohu](02-zaloha.md) globálního budíku pořízenou **před převodem** — celý dump, boot1 i `proinfo`
- `nvram.bin` ze svého čínského LX04
- **Windows 10** na jeden krok se SP Flash Toolem. Na Windows 11 se budík ve Správci zařízení vůbec neobjevil (přísnější podepisování ovladačů). Pod Wine SP Flash Tool nenaváže spojení (`STATUS_ERR (0xC0010001)`).
- SP Flash Tool, `DA_Mi_Hikaru-resign.bin`, `auth_sv5.auth` a firmware LX04 se scatterem ze složky `files/` projektu [AyraHikari/xiaomi-x04g-lx04](https://github.com/AyraHikari/xiaomi-x04g-lx04)
- Firmware SP6 — viz [03](03-lx04-na-sp6.md#firmware)

## Proč se to neobejde bez Windows

Čistě přes mtkclient převod nefunguje. Přepsání tabulky oddílů na rozložení LX04 (`wf gpt_lx04.bin`), boot1 vyčtený z funkčního LX04 (i s hlavičkou), kompletní SP6 i odemčený bootloader — výsledkem je pokaždé jen podsvícený černý displej.

Budík se rozběhl až po ručním formátu a zápisu přes SP Flash Tool. Ten při zápisu sám sestavuje hlavičku preloaderu a celou paměť připraví jinak než mtkclient. Který rozdíl přesně rozhoduje, není známé — ale tahle cesta funguje.

## Část 1 — Windows 10: SP Flash Tool

1. Zkopíruj do `C:\SPFT\` (cesta bez diakritiky a mezer):
   - složku `FlashTool`
   - `DA_Mi_Hikaru-resign.bin` a `auth_sv5.auth`
   - složku `Image` s firmwarem LX04 a scatterem
2. Nainstaluj ovladače: pravým na `C:\SPFT\FlashTool\driver\Mediatek-Drivers-Install.bat` → **Spustit jako správce**.
3. Spusť `_SPFT.exe` jako správce a nastav:
   - **Download-Agent** → `C:\SPFT\DA_Mi_Hikaru-resign.bin`
   - **Scatter-loading File** → `C:\SPFT\Image\MT8167_Android_scatter.txt`
   - **Authentication File** → `C:\SPFT\auth_sv5.auth`
4. Záložka **Format** → *Manual Format Flash*:
   - Region: `EMMC_USER`
   - Begin Address: `0x0`
   - Format Length: `0xEC000000`
   - **Start**, pak připoj budík v BROM režimu → „Format OK"

   *Format All + Download* nepoužívej — selže s `STATUS_UNKNOWN_STORAGE_SECTION_TYPE`, protože DA neumí formátovat boot oblast tohohle eMMC.
5. Záložka **Download** → režim **Download Only** → **Download** → připoj budík v BROM → zelené „Download OK".

Budík teď naběhne do čínského systému, ale skončí na hlášce **出现严重错误，需要恢复出厂设置** (závažná chyba, obnovte tovární nastavení). To je v pořádku — pokračuj na Linuxu.

## Část 2 — Linux: SP6 a identita

Všechno mtkclientem, každý příkaz s budíkem v BROM.

**SP6** — stejně jako u čínského budíku ([03](03-lx04-na-sp6.md#nahrání)):

```bash
source ~/mtkclient/mtk_venv/bin/activate
cd "cesta/k/Image sp6"

python3 ~/mtkclient/mtk.py w lk_a lk-verified.img
python3 ~/mtkclient/mtk.py w boot_a boot-verified.img
python3 ~/mtkclient/mtk.py w tee_a tee-verified.img
python3 ~/mtkclient/mtk.py w odmdtbo_a odmdtbo-verified.img
python3 ~/mtkclient/mtk.py w logo logo-verified.bin
python3 ~/mtkclient/mtk.py w system_a system.img
python3 ~/mtkclient/mtk.py w system_b system_other.img
python3 ~/mtkclient/mtk.py w vendor_a vendor.img
python3 ~/mtkclient/mtk.py w userdata userdata.img

cd ~/mtkclient
python3 mtk.py e userdata,metadata
```

Po startu teď uvidíš **未发现mi.did，请设置后，重启重试** (mi.did nenalezen). Chybí identita.

**Identita:**

```bash
python3 mtk.py w proinfo proinfo_x04g.bin   # vlastní, z tohohle globálního kusu
python3 mtk.py w nvram nvram_lx04.bin       # z tvého čínského LX04
```

- `proinfo` vrací globálnímu kusu jeho vlastní sériové číslo.
- `nvram` z LX04 přinese data, ze kterých si systém odvodí `mi.did`. Globální `nvram` je nemá — s ní hláška nezmizí.

Odpoj, zapoj normálně — naběhne úvodní průvodce LX04.

Pokud se start zastaví hned po logu (displej problikne a zhasne), je zamčený bootloader: `python3 mtk.py da seccfg unlock`.

> [!WARNING]
> Budík teď má MAC adresy čínského budíku, ze kterého `nvram` pochází. Vrať mu jeho vlastní — viz [Změna MAC adresy](#změna-mac-adresy) níž.

## Hotový převod si zazálohuj

Jakmile převedený budík funguje, ulož jeho stav. Další globální kus pak převedeš bez Windows:

```bash
python3 mtk.py rf zaloha_X04G_jako_LX04.bin
python3 mtk.py r preloader boot1_X04G_jako_LX04.bin --parttype boot1
```

## Další globální kus: naklonování (jen Linux)

Máš-li víc globálních budíků, stačí projít celý převod jen jednou. Na další kus zapíšeš hotový stav už převedeného budíku a vrátíš mu jeho vlastní identitu. Celé na Linuxu, bez SP Flash Toolu.

**1. Záloha nového kusu** — celý dump, boot1 i `proinfo` ([02](02-zaloha.md)). Budeš z ní potřebovat `proinfo`, `seccfg` a MAC adresy.

**2. Zápis hotového stavu a vlastního sériového čísla:**

```bash
python3 mtk.py wf zaloha_X04G_jako_LX04.bin
python3 mtk.py w preloader boot1_X04G_jako_LX04.bin --parttype boot1
python3 mtk.py w proinfo proinfo_novy_kus.bin
python3 mtk.py e userdata,metadata
```

Boot1 se tu mtkclientem zapsat dá, protože je vyčtený z funkčního zařízení i s hlavičkou.

**3. Vlastní `seccfg` a odemčení.** Záznam o zámku bootloaderu (`seccfg`) je šifrovaný klíčem konkrétního čipu. Ten z převedeného budíku je pro nový kus neplatný — `da seccfg unlock` skončí hláškou `Device is either already unlocked or algo is unknown`. Vrať novému kusu jeho vlastní `seccfg` z původní zálohy.

V záloze globálního budíku (původní rozložení X04G) leží `seccfg` na offsetu `0x3880000`, délka `0x40000`:

```bash
dd if=zaloha_novy_kus.bin of=seccfg_novy_kus.bin bs=4096 skip=14464 count=64
ls -l seccfg_novy_kus.bin            # musí být 262144 bajtů
xxd -l 0x10 seccfg_novy_kus.bin      # musí začínat 4d4d 4d4d ("MMMM")
```

Pokud velikost a začátek sedí:

```bash
python3 mtk.py w seccfg seccfg_novy_kus.bin
python3 mtk.py da seccfg unlock
```

Tentokrát skončí `Successfully wrote seccfg`. mtkclient zapisuje podle jména oddílu, takže ho umístí správně i do rozložení LX04.

**4. Start.** Budík naběhne s varováním **Orange State** (odemčený bootloader, start za 5 s) a pak do úvodního průvodce LX04.

> [!WARNING]
> Klon nese `nvram` převedeného budíku, tedy jeho MAC adresy. Oprav je hned — postup je níž. Sdílený zůstane i identifikátor `mi.did` pro cloud Xiaomi; pokud používáš asistenta Xiao AI na víc budících současně, počítej s tím, že je cloud může zaměňovat.

## Změna MAC adresy

Po převodu (i po klonování) má budík MAC adresy cizího kusu. Vrátíš mu vlastní na běžícím systému přes ADB — bez mtkclientu a bez BROM režimu.

MAC adresy jsou v souborech `/data/nvram/APCFG/APRDEB/WIFI` a `.../BT_Addr`. Mají na konci kontrolní součet, takže je nejde přepsat v hex editoru — použij skript [`zmen_mac.py`](../zmen_mac.py), který MAC zapíše a součet přepočítá.

**1. Zjisti vlastní MAC adresy budíku** ze zálohy, kterou jsi udělal **před převodem** ([02](02-zaloha.md)). Wi-Fi a Bluetooth mají každá svoji adresu:

```bash
python3 najdi_mac.py nvram.bin          # záloha oddílu nvram globálního kusu
python3 najdi_mac.py zaloha_full.bin    # nebo celý dump, trvá déle
```

Vypíše něco jako:

```
Wi-Fi      aa:bb:cc:dd:ee:01   (2x, prvni na 0x...)
Bluetooth  aa:bb:cc:dd:ee:02   (2x, prvni na 0x...)
```

Bez zálohy z doby před převodem vlastní adresy nezjistíš.

**2. Stáhni současné soubory** a pro jistotu celou složku nvram:

```bash
adb shell "cd /data && tar cf /data/local/tmp/nvram.tar nvram"
adb pull /data/local/tmp/nvram.tar nvram_zaloha.tar
adb pull /data/nvram/APCFG/APRDEB/WIFI WIFI_puvodni
adb pull /data/nvram/APCFG/APRDEB/BT_Addr BT_Addr_puvodni
```

**3. Vyrob soubory s novou MAC** (doplň svoje adresy):

```bash
python3 zmen_mac.py WIFI_puvodni    WIFI_novy    AA:BB:CC:DD:EE:FF
python3 zmen_mac.py BT_Addr_puvodni BT_Addr_novy AA:BB:CC:DD:EE:FF
```

Skript odmítne pokračovat, pokud vstupní soubor nemá správný tvar a součet — nic poškozeného do budíku nepošleš.

**4. Nahraj je do budíku:**

```bash
adb push WIFI_novy BT_Addr_novy /data/local/tmp/
adb shell "cat /data/local/tmp/WIFI_novy > /data/nvram/APCFG/APRDEB/WIFI && cat /data/local/tmp/BT_Addr_novy > /data/nvram/APCFG/APRDEB/BT_Addr && sync"
```

**5. Restartuj budík a ověř:**

```bash
adb shell cat /sys/class/net/wlan0/address
adb shell "dumpsys bluetooth_manager | grep -i address"
```

Kdyby se něco nepovedlo, vrátíš původní stav ze `WIFI_puvodni` a `BT_Addr_puvodni` stejným příkazem z kroku 4.

## Na závěr: zamknutí bootloaderu (volitelné)

S odemčeným bootloaderem ukazuje budík při každém startu varování **Orange State**. Až je všechno hotové a funguje, můžeš ho zamknout zpátky — budík pak startuje bez varování:

```bash
cd ~/mtkclient
source mtk_venv/bin/activate
python3 mtk.py da seccfg lock
```

Ověřeno na naklonovaném globálním kusu, po dokončení převodu i změny MAC.

Zamykej až úplně na konci. Během flashování musí být bootloader odemčený, jinak se start zastaví hned po logu. Kdyby se to stalo i po zamčení, odemkneš ho znovu přes `python3 mtk.py da seccfg unlock`.

Pokračuj na [Po instalaci](05-po-instalaci.md).
